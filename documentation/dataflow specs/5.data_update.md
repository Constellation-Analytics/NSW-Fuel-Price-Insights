# Module Spec: 5.data_update.py  

## 1. Module Overview  
- **Name / ID:** `5.data_update.py`  
- **Purpose:**  
  Executes core SQL stored procedures responsible for promoting validated staging data into production tables.  
  Each stored procedure conditionally updates fact and dimension tables based on data quality results in `dq_issues`.  
  Ensures controlled, idempotent, and logged data promotion.  
- **Author / Date:** Paul – 26 Feb 2026  

## 2. Upstream Dependencies  
- Orchestrator module (`orchestrator.py`)  
- Data quality module (`4.data_quality.py`)  
- Database staging tables generated by (`3.API_Integration.py`)  

- Environment variable:  
  - `DB_CONNECTION_STRING`  

- Stored Procedures:  
  - `update_fact_fuel()`  
  - `update_new_fuel_stations()`  
  - `update_updated_fuel_stations()`  
  - `update_inactive_fuel_stations()`  

## 3. Downstream Dependencies  
- Reporting layer (Power BI / Analytics consumption)  
- Production database tables:  
  - `fact_fuel_prices`  
  - `dim_fuel_stations`  

## 4. Inputs / Sources  

### Environment Variables  
- `DB_CONNECTION_STRING` – NEON database connection  

### Database Tables  
- `stg_fuel_price` – staged fuel pricing data  
- `stg_new_stations` – newly detected stations  
- `stg_updated_stations` – detected station updates  
- `dim_fuel_stations` – master station dimension  
- `dq_issues` – data quality defect tracking table  

### Stored Procedures  
- `update_fact_fuel()`  
- `update_new_fuel_stations()`  
- `update_updated_fuel_stations()`  
- `update_inactive_fuel_stations()`  

## 5. Outputs  

### Database Tables  
- `fact_fuel_prices` – populated with validated pricing records  
- `dim_fuel_stations` – updated with new, modified, or inactive stations  
- `sys_run_log` – logs procedure execution and affected row counts  

### Logging  
- Execution logs recorded in GitHub Actions workflow  
- Row counts logged via `sys_run_log` inside each stored procedure  

## 6. Logic / Processing Overview  

1. Establish PostgreSQL connection using `DB_CONNECTION_STRING`.  
2. Sequentially execute stored procedures:  
   - `update_new_fuel_stations()`  
   - `update_updated_fuel_stations()`  
   - `update_inactive_fuel_stations()`  
   - `update_fact_fuel()`  
3. Each stored procedure:  
   - Checks `dq_issues` for relevant defect IDs.  
   - Proceeds only if related defects = 0.  
   - Inserts or updates production tables accordingly.  
   - Captures `ROW_COUNT` using `GET DIAGNOSTICS`.  
   - Logs execution to `sys_run_log` regardless of row impact.  
4. Success/failure logged to workflow.  

## 7. Conditional Checks  

- Each stored procedure checks specific `defect_id` values in `dq_issues`.  
- If relevant issues exist → data update is skipped.  
- If no issues → data is promoted.  
- Database connection failure → raises exception.  
- Stored procedure execution failure → raises exception.  

## 8. Error Handling & Logging  

- Log connection attempts and procedure execution steps.  
- Stored procedures always log to `sys_run_log` (including 0-row operations).  
- Exceptions logged with stack trace.  
- Critical failures re-raised to orchestrator.  
- Workflow fails on unhandled exceptions.
